Purpose: let a maintainer with no context answer in 30 minutes (1) what the system claims, (2) what is proven and by which test, (3) what is not proven and why.
Run the audit tests with `python -m pytest tests/test_audit_accuracy.py tests/test_audit_completeness.py -q`; add `--runslow` to also run every test named in section 2 in one nested run.

Every statement here was checked against the code or a test run on that date; nothing is recalled from memory. Test ids are quoted exactly as pytest collects them (class-based tests carry their class).

### 3d. Known hazards

- Environmental clock event. What it is: a pause of the process or the machine (sleep, VM pause; D17 (9), (12)), which advances both the wall and the monotonic clock, so a test can appear to run for minutes or hours. How it is detected, four signals (D17 (12)): negative elapsed time; a negative remaining time in a failure's text; a wall/monotonic disagreement above 5 s; a heartbeat thread with 0.5 s ticks whose gaps above 5 s mean the process was not scheduled (heavy CPU load does not do that: the 36-burner runs never tripped it). What the runner does: a FAILED test in such a window is reported as SKIPPED with the reason `environmental interruption: <reason>; run_id=...`; the closing line begins `INVALID RUN (clock event): N environmental interruption(s), run_id=...`; the exit status is non-zero (an invalid run is never green); the run is not recorded in `.perf/history.json`. Known cost: a REAL failure that happens to coincide with a pause is also skipped; the run is flagged invalid and exits 1, and a re-run shows the real failure. Also: a test that fakes a clock by patching `time.monotonic` or `clock_guard.elapsed` globally is itself seen by the real detector; fake clocks must be injected.
- Windows Application Control blocks `import anthropic` on the build machine (its `jiter` DLL is blocked), so the repository uses a plain-httpx Messages API client (the ingest.anthropic_http module, shared by the doc path and the planner). `ANTHROPIC_AUTH_TOKEN` is no longer accepted: setting it without `ANTHROPIC_API_KEY` raises a loud error naming the fix (D16, D20).
- Laptop sleep. A sleep mid-run produced a 47,090 s (13 h) suite run once and corrupted the first budget derivation (D17 (7)); the measuring script now excludes any run over 3x the median run and any record over 10x its own budget. A sleep during a normal pytest run is handled by the clock-event machinery above.

## 5. HOW TO CLOSE THE JUDGMENT GAPS

Run `python scripts/live_run_ceremony.py --allow-live --upstream https://httpbin.org/status/418` with `ANTHROPIC_API_KEY` set in the shell. It runs the three subcommands (`--planner`, `--doc`, `--apply`) in order, stops at the first failure, moves the passed rows from section 3a to section 2b, and commits each with its record hash. It will refuse to move a row without a fresh `real: true` pass, and it refuses to start without both the key and `--allow-live`; a mock, a wrong key, a loopback upstream, a skip or an old run can never move a row. Step 4 is opt-in because it sends real requests to five third-party APIs; their outages are not the ceremony's failure: add `--include-live-apis` to run it (it moves C26 only if all 14 live-API tests pass against all five hosts). To run each step individually, see docs/LIVE_RUN.md.

## 6. WHAT IS LEFT AFTER THE CEREMONY

After a successful live ceremony, three rows move from section 3a to section 2b: the real-model planner judgment, real doc extraction against a live model, and the learning loop against a real upstream failure (their ids are in section 3a). Those three gaps need something outside this repository, and the system is otherwise complete. There are two honest ways to get it, and a third item that is not a way to close a row (D32):

1. Anthropic credits. The ceremony command in section 5 works unchanged once the key has credit; it is the only path that closes the three rows, because their judgment is Claude's. The 2026-11-13 attempt stopped at step 1 on a billing error and moved nothing.
2. GPU inference for a free provider (a local GPU, or a hosted free tier fast enough). It would prove the WIRING on a real model: the section 7 runs that timed out on this CPU would finish and be judged on their merits. It would still not close the three rows: a free-provider pass is `real: false` and `move_audit_row.py` refuses it with exit 19 (D27, D29).
3. A model quality evaluation that says which Claude tier is minimally sufficient. This is what a procurement decision would need, and it is not built. It does not close a row either; it is recorded in section 3d as a known unknown, not as a claim.

The remaining unproven claims are: C26 (Live-API behaviour of the five real-API servers); C28 (Mixed approved and unapproved proposals in one apply call); C29 (Same-second handoff filenames do not overwrite each other); C30 (Retail outage probe); C31 (Non-outage failures such as KYC rejection in cross-industry scenarios); C10 (Orphan-handoff detection); C11 (Cost / token accounting); C39 (Duty matching on real phrasing); C40 (Induction from real-model runs, and replay on a real system); C42 (Binding and example robustness); C43 (Shipped duties on real systems); C49 (Approval of a pending write is safe against a changed world, and resumes the run); C50 (A tool's declared `reversible` is true); C58 (Non-Anthropic providers (Ollama, freellmpool, OpenRouter)); C66 (The docs deploy workflow (.github/workflows/docs.yml)). Nothing else changes.

### What was proven

- Request shape accepted. Ollama's `/v1/messages` took the Messages request body unchanged (HTTP 200, an Anthropic-shaped answer, `x-api-key: ollama`) and the plain-httpx client parsed the reply, including a `thinking` block that `qwen3.5` puts before its answer.
- `tool_use` parsed (`qwen3.5:4b`). A 2-tool `submit_plan` request came back as a real `tool_use` block with the correct plan. This depends on the model: `qwen2.5-coder:7b` wrote the call as JSON inside a `text` block, which the planner would reject as `PLANNER_NO_TOOL_CALL`. That was handled by choosing the model; no provider setting was tuned.
- The apply loop passed (record `45b5bca75175`) against a loopback upstream that answers 418: generate, run, collect, propose, simulated approval, apply, verify, commit. No model takes part in that step and the upstream is loopback, so it is `real: false`; it shows the harness's pass path, not a judgment.
- The provider-gated refusal is correct. `move_audit_row.py` refused C24 (planner records `31fb6a8aa5e6` and `b937a16afbc6`), C25 (doc record `f594e119b347`) and C27 (apply record `45b5bca75175`) with `REFUSED (PROVIDER)`, exit 19, and `AUDIT.md` was byte-identical afterwards. Every record has `closes_gap` null.
- One harness gap was found and fixed: a free-provider run could not start, because the harness and the live-gated contract tests unlocked only on `ANTHROPIC_API_KEY`. The gate is now `provider_config.credentials_present()`; the tests' assertions are unchanged.
- The registry filter (D31) is correct, deterministic and tested (section 2, C61). That is a property of the code, not a latency result: see below.

### What was NOT proven

- The planner within a CPU inference budget with the FULL registry: the harness step timed out at 240 s (records `be0c06405af5` with `qwen2.5-coder:7b`, `31fb6a8aa5e6` with `qwen3.5:4b`). A 2-tool request alone took 31.7 s (`qwen2.5-coder`) and 81.4 s (`qwen3.5`).
- The planner within that budget with a FILTERED registry (D31, `PLANNER_MAX_TOOLS=8`, record `b937a16afbc6`). The filter FIRED: filtered registry reduced 31→8 tools for the first intent and 31→5 for the second (intents 3 to 10: 31→7 and then 31→8 for each of the other seven; 24 distinct tools across the ten requests); planner still exceeded 240s on CPU (wall 243.1 s). WHERE THESE NUMBERS COME FROM: the record has NO registry fields (the harness does not record them) and the planner's stats file was never written because the plan never finished. The per-request sizes are recomputed offline with the same deterministic function (`registry_filter.select_tools`); the live sizes of the first two requests (8 and 5 tools) were observed in a direct two-intent run, which is not a harness record. Was the reduction enough? No. Those two requests took 80.7 s (8 tools) and 104.9 s (5 tools): each under the client's 120 s, but a plan is at least ten requests (roughly 800 to 1,050 s at that rate, an estimate, against the 240 s step), and the earlier UNFILTERED requests of only 2 tools took 31.7 s and 81.4 s, so on this machine the time does not follow the number of tools. Wiring verified; planner exceeds CPU inference budget even with filtered registry. No timeout was raised.
- Doc extraction within the client timeout: `ReadTimeout` at the client's 120 s (record `f594e119b347`).
- Model quality (not wiring): qwen3.5:4b returned a parseable `tool_use` block for "book a seat" (intent `book_flight_for_passenger`) that mapped to `travel__search_flights`, a search tool, not the booking tool. Free providers verify the wire format and the parser, not plan quality. It does not reject it for the tool choice: `check_each_intent_once_with_a_tool_of_its_declared_industry` compares a tool's industry (travel), not which travel tool, so a full plan with only that choice swapped passes all four checks (run 2026-11-15).
